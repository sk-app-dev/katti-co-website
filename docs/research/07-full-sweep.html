The number that changes things

Vaquill's index is 463.6 GB, and I have been treating that as the cost of doing this. It isn't. That figure is a consequence of their choices — 1024-dimension vectors, unquantized, across the whole country.

Re-embedding Karnataka High Court ourselves with a small model: 2.2 GB, or 0.56 GB quantized. The entire Indian corpus, all 32.5M chunks: 46.5 GB, or 11.6 GB quantized — against their 463.6 GB. A 10–40× reduction, from dimension choice and quantization alone. The scale question I have been treating as a real constraint mostly is not one.

02

What the remaining files held

I was wrong about the superseded trap — it's already fixed

Good news, my error

Last time I told you any build on the legislation data must handle superseded itself or risk telling a client a dead RBI direction is current. Reading schema.py: the published parquet carries a computed in_force boolean with the taxonomy repair already applied.

So the trap exists in their internal Qdrant payloads and in their own published spreadsheet — but not in the data we'd actually download. Use in_force, don't derive from act_status, and it's handled. I over-warned.

The legislation schema is richer than I realised

Genuinely useful

Beyond section text, each provision carries: legal_subject, provision_type, doc_type, department, regulatory_body, acts_referenced, defined_terms, amendment_count, and two that are quietly excellent — has_proviso and has_non_obstante.

A non-obstante clause ("notwithstanding anything contained in…") is exactly the thing you want to find fast when arguing which provision overrides which. Being able to filter for it across 1.1M provisions is a real research capability, and it's free.

The court field was never normalised — 49 labels for 26 courts

Would silently break search

Karnataka is stored as High Court of Karnataka, not "Karnataka High Court". Telangana is stored as High Court for State of Telangana — with a double space. Their own audit says it plainly: any query filtering on an exact court string silently misses the variants.

This is the kind of bug that returns plausible-looking incomplete results rather than an error. Whatever we build must normalise court names on the way in.

The v2 collection is mislabelled in two separate files

Trust the audit, not the docs

Both the README and QDRANT_RESTORE.md describe legal_corpus_v2 as "tribunal and regulator decision chunks." The audit, generated from live Qdrant with exact counts, shows v2 holding Karnataka's 581,275 cases, Kerala's 916,187, and the Supreme Court's 371,159 chunks. It is High Court and Supreme Court material, not tribunal.

So my original instinct was half right after all: the labelling genuinely is wrong, in two places, and the tribunals audit explains where tribunal data actually lives — Supabase tables and R2 PDFs, never in any vector collection. Where the docs and the measured audit disagree, the audit wins.

An eCourts API report with real prices — and a silent-failure warning

Directly actionable

An undocumented gift: ECOURTSINDIA_API_DISCREPANCY_REPORT.md, a live-tested bug report against the third-party eCourts API, listing per-call costs — search ₹0.20, case detail ₹0.50, cause list ₹1.00, AI order analysis ₹2.50.

That prices the cause-list idea concretely: roughly ₹30/month for a daily check. It also confirms advocates is a real search parameter, and lists actual case-type codes including ITA (Income Tax Appeal), Tax_Ref, COP (Company Petition), ARB_PET and RERA — this firm's forums exactly.

The warning matters as much: the documented filter values are wrong, and using them returns zero results with no error. Their report is the correction sheet for an integration we might otherwise have built blind.

The licensing position is stronger than "CC BY"

Reassuring

coverage.yml records the actual legal basis: Copyright Act 1957 s.52(1)(q), with the text a Government work under s.17(d). Release cleared by counsel in August 2026. Their policy excludes commercial law reporters entirely, citing EBC v. Modak — the case on copyright in copy-edited judgments — and excludes aggregators.

They also note India has no government-edicts doctrine, so US reasoning doesn't transfer. For a law firm relying on this, that reasoning being written down and counsel-reviewed is worth more than the licence label alone.

The embedding pipeline is not in the public repo

Scope limit

requirements.txt has no ML dependencies at all — just scraping, PDF parsing and pandas. So what's published is the scraping and parsing pipeline. The chunk schema is documented, but the code that embeds and indexes is theirs and stays theirs.

Which is fine, because we're building that part ourselves anyway — but it means "fork their pipeline" was never quite the option I implied.

04

Two indexes, not one

Mitra and the internal search tool run in different places, so they need differently-sized indexes. Treating them as one system was a mistake in my earlier plans.

Mitra's index — small, hosted, always on

Runs on
Vercel serverless — cannot hold a multi-GB index in memory, and cold-starts
Implication
Needs a hosted vector store it queries over the network, plus an embedding API call per question to turn the visitor's query into a vector
Size it to
~150K chunks — practice-area legislation plus a curated set of judgments. 50 MB quantized, which fits free hosted tiers comfortably
Watch
Every query costs one embedding API call. Mitra already uses over half its Gemini free-tier ceiling, so this needs its own budget

The internal tool's index — large, local, on demand

Runs on
Your machine, on demand, with the GPU present
Implication
No hosting limit, no per-query API cost — embed the query locally on the same GPU
Size it to
Full Karnataka, or more. 0.56 GB quantized, trivial on an SSD
Watch
Only available where the machine is — which is the tradeoff we already discussed

Same source data, same embedding model, two differently-scoped builds. The internal one can be enormous because nothing is hosting it; Mitra's must stay small because a serverless function has to load and query it on every request from a stranger.

05

Critique of the MCP plan

I proposed this enthusiastically and undersold its limits. It's still the right choice for the internal tool — for narrower reasons than I gave.

It does nothing for Mitra, and I blurred that

Real limitation

An MCP server is a tool a human's AI client calls. It is not a backend a website can use. Mitra answers strangers at 3am with nobody driving — it needs its own hosted API and always will. Anywhere I implied MCP was part of Mitra's architecture was wrong.

Search results will eat the context window

Design constraint I never mentioned

Chunks are ~4,096 characters. Ten results is ~40,000 characters — roughly 10,000 tokens for a single search. A few searches and the conversation is full, which degrades everything after it.

The fix, which has to be designed in rather than added later: the search tool returns citations, court, date, disposition and a two-line snippet — never full chunks. A separate fetch_full_text tool retrieves one document when you actually want it. That's a materially different tool design from "return the top 10 matches."

The terminal is the wrong front door for a lawyer

Fix is easy

I kept describing this as "connect it here in Claude Code" — a developer tool. For daily research use, Claude Desktop is the right client: a normal application, same MCP server, no terminal. Worth setting up that way from the start rather than migrating later.

Publishing it publicly deserves more caution than I gave

Reconsider

I twice framed an open-source India legal MCP server as a visibility and credibility play for the firm. Given Rule 36, "credibility play" is precisely the framing to avoid — and a software tool isn't obviously covered by Rule 51's protection for legal writing and scholarship the way an article would be.

If it's published at all, the defensible version is a genuine open-source contribution under a personal or neutral identity, not firm-branded, with no promotional framing. Or simply keep it internal, which costs nothing and removes the question entirely.

Where it genuinely is the right answer

Holds up

For the internal tool specifically, MCP remains excellent: zero new infrastructure, zero LLM cost beyond what you already have, and the reasoning is done by a strong model rather than something small running locally. Build the search index once, expose it as a handful of tightly-scoped tools, and it's usable immediately without building any interface at all.

That was the right instinct. The mistake was implying it was a general answer rather than a good answer to one specific problem.
