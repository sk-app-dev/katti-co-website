01

Open India Law

The centerpiece of the find — free, structured, and large enough to replace both a paid case-law subscription and weeks of manual knowledge-base curation.

Coverage

  • 12,848,644 court judgments — Supreme Court and all 25 High Courts, 1950–2025, chunked into 32,572,660 parquet rows
  • 813,168 tribunal/regulator matters — 15 forums including ITAT, NCLT, NGT, CESTAT, each as a separate file
  • 22,265 acts, 1,098,577 sections — central, state, and union territory legislation, 1806–2026, with in-force/repealed/amendment status
  • 32,518,048 vectors pre-computed (Voyage AI voyage-4, 1024-dim) across three Qdrant collections — the slow, expensive part of building search is already done

Access

  • Hugging Face: load_dataset("vaquill/open-india-law", "judgments")
  • Direct parquet downloads from mirrors
  • Qdrant snapshot recovery for the vector collections (their own QDRANT_RESTORE.md covers shard setup and disk requirements)
  • A browsable web UI for the 22,264 acts with source PDFs

License

Scripts: Apache-2.0. Compiled data: CC BY 4.0. The underlying legal text itself needs no permission at all — it's government work, reproducible under s.52(1)(q) of the Indian Copyright Act. The one real obligation is attribution on the compiled dataset, which the maintainers are explicit isn't their preference but a condition their own government/tribunal sources impose.

02

What this unblocks

Two things scoped earlier that were each blocked on a real decision — both resolved now.

Internal case-law research tool

Was blocked on choosing between a paid subscription (SCC Online/Manupatra, real licensing questions) or scraping court sites ourselves from scratch. That decision is moot — this is free, already covers Supreme Court through every High Court and 15 tribunals, and the expensive step (embedding 32.5M chunks) is already done. What was a multi-phase build collapses into: download, load into a vector store, ship a search UI.

Mitra's knowledge base

The plan was to manually curate acts and landmark judgments per practice area — real time, mostly yours. The core acts for IP, tax, and corporate law are almost certainly already in here, structured and sectioned, with real judgments to cite alongside them instead of hand-written summaries. Curation work shifts from "write this from scratch" to "select and verify what's already structured."

03

Working tools worth forking

Four repos in the same org that are already-built, not just data — each shortens something we'd otherwise build from zero.

contract-debugger Next.js · React · Tailwind

A complete, working app: upload a contract, GPT-4o flags risky or unfavorable clauses in plain English with severity ratings and suggested rewrites. Same stack as the firm's own site. This is the fastest path to a real internal tool — fork it, swap in Gemini, adjust prompts for Indian contract conventions. Days, not weeks.

ms-word-addin Apache-2.0 · BYOK

The fuller version of the same idea, live inside Word: chat with cited sources, automated review with tracked changes, draft-from-description, document finalization tools. The "community" build is fully self-hostable on your own Gemini key — no dependency on Vaquill's servers. Bigger lift than contract-debugger, but the natural next step once an MVP earns its keep.

open-legal-answer-benchmark MIT code · CC BY 4.0 data

Right now every judgment we've made about Mitra's answer quality has been eyeballing screenshots. This is a reproducible scoring methodology — checks that key facts appear, that citations actually support what's claimed, that wrong-jurisdiction authority doesn't leak into an answer — explicitly built for reuse with a different question set. Write 30–50 India-specific test questions in their format, reuse their scoring script, get real before/after numbers on every future Mitra change.

vaquill-mcp / courtlistener-mcp / canlii-mcp pattern, not data

Each of these wraps a legal API as an MCP server so any Claude- or Gemini-based tool can query it directly. Vaquill's own US version needs their paid API — but the pattern (FastMCP auto-generating tools from an OpenAPI spec) is exactly the shape of something we could build on top of our own self-hosted Open India Law data instead.

04

Beyond chatbot, drafting, search

An open-source india-law-mcp server

Build the same wrapper pattern above, pointed at our own hosted Open India Law data instead of a paid API. Useful internally — Indian case-law search available to Mitra, to the drafting tool, and to me directly in future sessions doing research for you. Given Aprameya's own background, publishing this back to the open-source community is also a real credibility and visibility play for the firm, not just an internal utility.

Multilingual Mitra, with an actual quality bar

legal-mt-benchmark is evaluation-only — no usable translation model — but it proves there's already real rigor applied to English↔Hindi legal translation quality (a 500-sentence benchmark built with IIT Patna, checking legal-term accuracy specifically). If Mitra ever answers in Hindi or Kannada for clients more comfortable there, this is the methodology to hold it to, not a "translate and hope" approach.

Playbook structure as a template, not content

The 28 negotiation playbooks in the playbooks repo are US-specific and not directly usable, but the format — clause-by-clause, both-sides framing (customer vs. vendor), strategic language recommendations — is a solid structural template for what the firm's own Indian-context contract playbooks should look like, if and when the drafting tool needs them.

Open decisions

  • Scope the vector index, don't load all of it. 463.6 GB uncompressed for the full 32.5M vectors is real infrastructure cost. A smaller, targeted subset — Karnataka High Court plus the practice areas Mitra already covers, say — is very likely enough, and dramatically cheaper to host.
  • Decide a refresh cadence. This is a fixed snapshot, not a live feed. Legal research on stale data is a real risk, not a cosmetic one — worth deciding upfront how often to re-pull (their next snapshot release, or running their scrapers ourselves) before this becomes load-bearing for anything client-facing.
  • Bake in attribution wherever this data surfaces — in the internal tool's UI, and in Mitra's own answers if its knowledge base draws from this — since it's a condition of the license, not a courtesy.
