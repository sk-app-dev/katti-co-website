Mitra

Live — no rebuild needed

Free, public, on the website. Already working.

Nothing in this plan touches Mitra. The one optional future link between it and the search bot below: once the search bot's Karnataka-HC-plus-legislation data exists, Mitra's knowledge base could eventually draw from that same verified data instead of hand-written entries — but that's a later decision, not part of building the other two systems.

Search bot

To build — internal first

Firm-only for now. Commercialize later once it's proven internally.

What it is

A private tool that searches real Karnataka High Court judgments, Central legislation, and the regulators matching our practice areas — reachable through Claude Code/Desktop as an MCP server, so no separate app or login is needed to start using it.

  • Phase 1

    Download the scoped slice from Hugging Face (vaquill/open-india-law) — Karnataka HC judgments, Central legislation, and the regulator files matching our six practice areas.

    Free, CC BY 4.0. Lands on the local SSD, not the cloud.

  • Phase 2

    Index it with SQLite FTS5 — plain keyword search over the real text. No embeddings, no vector database, nothing to pay for.

    This alone is already a real upgrade over hand-written KB entries — actual judgments and actual section text, searchable.

  • Phase 3

    Build the MCP server (Python, FastMCP-style) exposing search_judgments() and search_legislation() tools over that index. Connect it here, in Claude Code.

    No LLM API key needed for this — Claude's already doing the thinking through this session.

  • Phase 4

    Optional upgrade: add semantic search. Re-embed the same scoped slice using Gemini's free-tier embeddings (not Vaquill's Voyage vectors — different model, different space, can't mix them), store in Chroma alongside the keyword index.

    Only worth doing once keyword search has been used for a while and its gaps are actually felt.

Cost: $0 Storage: local SSD Access: Claude Code / Desktop via MCP
Commercializing later: the MCP server and index are the hard part, and they're already built for us by then. Turning it into something sellable to other firms is mostly a packaging exercise — a simple hosted web UI wrapped around the same backend, plus hosting and billing for other firms' access. Not a rebuild.

Draft bot

To build — internal first

Firm-only for now. Commercialize later.

What it is

A self-hosted fork of Vaquill's ms-word-addin — first-draft generation for notices, replies, opinions, and contracts, inside Word, running on our own Gemini key.

  • Phase 1

    Fork the already-cloned repo, set VITE_EDITION=community. This build has no dependency on Vaquill's servers at all.

  • Phase 2

    Point it at Gemini using the same API key Mitra already uses. Build the static add-in files and sideload the manifest into Word.

    Sideloading is standard for a personal/internal add-in — no Microsoft Store publishing needed.

  • Phase 3

    Add a thin server-side proxy for the Gemini key — same pattern as /api/mitra already uses — so the key never sits in client-side code. Host it free on Vercel, alongside the main site.

  • Phase 4

    Optional: feed in our own redacted past documents as style templates, replacing the repo's default US-oriented ones, so drafts come out in the firm's actual voice and structure.

Cost: $0 (Gemini free tier, same as Mitra) Hosting: Vercel free tier License: Apache-2.0
Commercializing later: same shape as the search bot — the app itself is already built and self-hostable. Selling it to other firms means hosting and supporting it for them (their own key or a metered shared one), not rebuilding the core product. Lexlegis.ai charges ₹9,000+/user/month for a more elaborate version of this same idea — real room to price under that.

Suggested order

  1. Draft bot first — the repo is already mature and complete; forking and configuring it is the fastest path to something real and usable, likely a day or two of work.
  2. Search bot second — genuinely useful but needs actual data download and indexing work before it's usable, not just configuration.
  3. Revisit Mitra last, and only if the search bot's verified data turns out to be worth folding into its knowledge base.

Reasonable to reverse this if research is a bigger daily need than drafting right now — this is a suggestion, not a fixed sequence.
